# Level 5 — Doc 10: Contextual Retrieval (Anthropic) ⭐

> **Goal:** Chunking loses surrounding context. Contextual Retrieval prepends a chunk-specific explanation BEFORE embedding — cuts retrieval failure rate by ~35-49% (Anthropic's own benchmarks).

---

## 1. The Problem This Solves

```
Original document: "The company's revenue grew 3% over the previous quarter."

This chunk, in isolation, is USELESS for retrieval — which company?
which quarter? A query like "What was Acme Corp's Q2 2024 revenue growth?"
won't match this chunk well via embeddings OR BM25, because the chunk
itself never mentions "Acme Corp" or "Q2 2024" — that context lived
elsewhere in the original document, before chunking split it away.
```

This is the fundamental tension in chunking (already covered in
`04_chunking_strategies.md`): smaller chunks = more precise retrieval
granularity, but LOSE the surrounding context that makes a chunk
meaningfully searchable in the first place.

---

## 2. The Technique

```
For EACH chunk, before embedding it:
1. Send the FULL document + that specific chunk to an LLM
2. Ask the LLM: "Give a short context explaining what this chunk is about,
   situated within the full document"
3. PREPEND that generated context to the chunk
4. Embed the CONTEXT-AUGMENTED chunk (not the original bare chunk)
```

```python
from anthropic import Anthropic

client = Anthropic()

CONTEXT_PROMPT = """<document>
{full_document}
</document>

Here is the chunk we want to situate within the whole document:
<chunk>
{chunk_content}
</chunk>

Give a short succinct context to situate this chunk within the overall
document for the purposes of improving search retrieval of the chunk.
Answer only with the succinct context and nothing else."""

def contextualize_chunk(full_document: str, chunk: str) -> str:
    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=200,
        messages=[{
            "role": "user",
            "content": CONTEXT_PROMPT.format(
                full_document=full_document, chunk_content=chunk
            ),
        }],
    )
    context = response.content[0].text
    return f"{context}\n\n{chunk}"   # prepend context BEFORE embedding

# Before: "The company's revenue grew 3% over the previous quarter."
# After:  "This chunk is from an SEC filing on ACME Corp's Q2 2024
#          performance; the previous quarter refers to Q1 2024.
#
#          The company's revenue grew 3% over the previous quarter."
```

**Why send the FULL document per chunk (seems wasteful)?** This is exactly
where **prompt caching** (already covered in `Level3_LLM_APIs_SDKs`) makes it
economical — cache the full document once, then only the (cheap) per-chunk
portion of the prompt changes across calls. Anthropic's own reference
implementation reports this makes contextualizing an entire knowledge base
cost-effective, not prohibitively expensive.

## 3. Combining with Existing Techniques (this repo's coverage)

```
Contextual Retrieval STACKS with what you already know:

Contextual Embeddings   → fixes the "chunk lacks context" embedding problem
       +
Contextual BM25          → same context-prepending trick, applied to the
                            keyword-search side too (06_hybrid_search.md)
       +
Reranking                → still run reranking (07_reranking.md) AFTER
                            retrieval — contextual retrieval improves what
                            gets INTO the candidate set; reranking still
                            improves the final ordering
```

Anthropic's benchmark numbers (order of magnitude, not exact for your
dataset): contextual embeddings alone → ~35% fewer retrieval failures;
contextual embeddings + contextual BM25 → ~49% fewer; adding reranking on
top → ~67% fewer failures, vs a naive chunking-only baseline.

---

## 4. When NOT to Bother

| Situation | Verdict |
|---|---|
| Chunks are already self-contained (e.g., FAQ entries, one Q&A per chunk) | Skip — no missing context to restore |
| Documents are short enough to not need chunking at all | Skip — irrelevant |
| Cost-sensitive, low query volume, "good enough" retrieval acceptable | Skip — extra LLM calls per chunk at ingestion time add cost/latency to your pipeline, even with caching |
| Large corpus of long, context-dependent documents (legal contracts, financial filings, technical manuals) | **Use it** — this is exactly the scenario it was designed for |

## Interview Q&A

**Q: How is Contextual Retrieval different from just using bigger/overlapping chunks?**
A: Bigger chunks trade off retrieval precision for more context — you get
the context back, but lose the ability to retrieve narrowly. Contextual
Retrieval keeps chunks SMALL and precise, but adds back just enough
situating context (generated by an LLM) so the small chunk is still
meaningfully searchable on its own.

**Q: Isn't sending the whole document per chunk to an LLM extremely expensive at scale?**
A: It would be, without prompt caching — the full document is the
expensive, repeated part of the prompt across all its own chunks, and
caching it means you pay full price once per document, not once per chunk.

**Q: Does Contextual Retrieval replace reranking?**
A: No — they solve different problems and stack together. Contextual
Retrieval improves what makes it INTO your top-K candidates in the first
place; reranking still improves the final ordering of those candidates
before they reach the LLM.
