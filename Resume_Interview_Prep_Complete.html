WARMUP

Walk me through the Laravel-to-Django migration. What was the actual business driver — why spend a year rewriting working software?

💡 Lead with business, not tech religion: deploy coupling on revenue-critical invoicing, Python/Odoo ecosystem consolidation, async processing needs. 'Rewrite because PHP is old' is a failing answer.

CORE

Kitni services hain exactly? Each one independently deployable hai? Deploy pipeline alag hai har ek ka?

💡 THE drill for this resume. Give a true count (likely 2-4 units: Django app, Odoo, Celery workers) with deploy story for each. Claiming 8 services then fumbling on 'show me the pipelines' = interview over.

CORE

How did you decide service boundaries? Why is Invoicing separate from Operations — and who owns the customer table?

💡 Boundary by business capability + change frequency + failure isolation (invoicing must not go down with ops). Customer master: one owner, others hold IDs/read replicas via API or events — say it crisply.

TRAP ⚠

Your Django services and Odoo all talk to the same PostgreSQL, don't they? Shared database across microservices is an anti-pattern — defend it.

💡 The most predictable trap for any 'Django microservices' resume in India. Don't bluff separate DBs if reality is shared: defend with schema/table ownership per service, no cross-service table writes, no cross-boundary joins; concede DB-per-service buys isolation but costs distributed transactions + recon tooling — wrong trade at this team size and scale. Naming the anti-pattern yourself and showing it was a conscious trade-off scores; pretending isolation that doesn't exist fails on the next question.

CORE

Big bang ya incremental cutover? Ek module migrate ho gaya, baaki Laravel pe hain — dono systems ek saath kaise chale?

💡 Strangler: route-level switch at nginx, migrated module's old code flipped read-only, shared auth/session strategy, recon job comparing both systems' outputs during parallel run before decommission.

DEEP

During the transition window an invoice could be touched from both systems. How did you prevent double writes / split-brain?

💡 Single writer per module at any point in time — ownership flips atomically at cutover; old paths return 410/redirect; financial tables had a freeze window during the flip. If you had dual-write, explain conflict resolution honestly.

DEEP

How did you validate the data migration — how do you KNOW nothing was lost from 100 Cr worth of financial records?

💡 Row counts per table, sum-of-amounts checksums per period (totals must match to the paisa), spot-sample audits with finance team sign-off, and the migration scripts kept re-runnable/idempotent.

TRAP ⚠

Microservices for a team of how many developers? Wasn't that overengineering?

💡 Concede gracefully: 'coarse-grained services, chosen for deploy isolation of revenue-critical invoicing — not Netflix-style 50 services'. Showing you know the microservices tax (ops, distributed debugging) earns more than defending the buzzword.

CORE

Reduced ORM query time by 60% — 60% of WHAT? Show me one query before and after.

💡 Need one concrete: e.g., invoice list API 2.5s → <1s. Diagnosis via django-debug-toolbar / connection.queries / EXPLAIN ANALYZE; fix = composite index on (company_id, invoice_date) + select_related/prefetch_related killing N+1. Memorize YOUR real numbers.

CORE

What went wrong in the migration that you didn't anticipate?

💡 Have one true story with a fix: float vs Decimal rounding diffs in migrated amounts, MySQL→Postgres collation/date quirks, or a missed FK orphan batch. 'Nothing went wrong' is an instant credibility hit at 4+ years.

DEEP

If you did this migration again today, what would you do differently?

💡 Senior signal: e.g., invest in recon tooling on day 1, migrate the smallest module first to derisk the pattern, contract tests between old/new, feature flags instead of nginx-only switches.

WARMUP

Why rebuild on Odoo 17 instead of upgrading 15 in place? That sounds expensive.

💡 Driver = single-company → multi-company re-architecture: every custom module's data model and record rules needed rework anyway; 2-version jump (15→16→17) of 57 custom modules via OpenUpgrade-style scripts was riskier than a clean rebuild + data migration.

CORE

How does Odoo guarantee Company A's user never sees Company B's invoices? At which layer is that enforced?

💡 ORM layer via ir.rule record rules: domain like ['|', ('company_id','=',False), ('company_id','in',company_ids)] evaluated on every read/write; user's allowed companies from res.users. NOT view-layer filtering — say that explicitly.

CORE

PAN/contact master shared hai sab companies me — design kaise kiya? Duplicate PAN aaye to?

💡 res.partner kept global (company_id False) so one customer = one record across companies; PAN as constrained/validated field (MasterIndia API verification), dedup check on create — merge flow for existing duplicates. Edit rights on shared masters restricted to a role.

DEEP

User has access to both companies, company switcher is on Company B, but he's working Company A's order — what bug class does this create and how did you defend?

💡 Classic wrong-company-record bug: defaults pull company from context. Defense: explicit company_id defaults derived from the parent record (order → invoice inherits company), record-rule tests, and computed checks (_check_company on related records).

DEEP

99% SAP success across 10,000+ invoices — that's ~100 failures a month. Pick one failed invoice and walk me through its entire life.

💡 The single most predictable drill on this resume. Trace: push fails (say SAP timeout) → row in sync_log with payload + error + status → auto-retry x3 exponential backoff → still failed → appears on ops dashboard → root cause (missing customer code in SAP) → master data fixed → manual replay button → recon job confirms posted. Also define the metric: successes/attempts measured from sync logs.

CORE

Explain the AR auto-blocking by PAN aging 15/40 days — why PAN-level and not customer-level?

💡 One business entity = one PAN but may exist as multiple partner records/companies — aging by PAN stops the dodge of ordering through a sister account. 15 days = warning/soft action, 40 = hard block on confirmations; cron-driven, finance can override with approval.

TRAP ⚠

Two of your 12 crons touch the same invoice at the same moment — monthly generation and SAP sync. What happens?

💡 Know Odoo's cron concurrency model (a cron job is locked while running; workers don't double-run the same job) AND your own guards: state-machine checks (only sync invoices in 'posted'), idempotent operations, row-level locking where needed. 'It just works' fails the question.

CORE

Odoo ORM vs Django ORM — biggest differences that bit you?

💡 Recordsets vs querysets, active-record style write/create, @api.depends compute fields + recomputation storms, sudo() privilege escalation footgun, no select_related equivalent — prefetching is automatic but loops over browse still hurt. One real gotcha story each.

CORE

What is EDI e-invoicing in the Indian context and what did your module do?

💡 GST e-invoicing: B2B invoices registered with IRP to get IRN + signed QR; your module built the JSON payload, called the provider (MasterIndia), stored IRN/QR on the invoice, handled rejections. Know IRN basics — it's on your resume via 'EDI e-invoicing' + 'MasterIndia (GST/PAN)'.

▶Story 3: Niroskos multi-tenant safari platform (+ 50,000 daily transactions / state machine / django-hosts claims)11 Q · 4 drillsP0 · MUST

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Multi-tenant means what exactly in your platform — separate databases, separate schemas, or shared tables?

💡 One-sentence answer + why: shared schema with tenant FK fits many small safari operators (cheap ops, easy cross-tenant admin); trade-off acknowledged: weaker hard isolation, so enforcement lives in the query layer. Knowing the OTHER two models is mandatory.

CORE

Request aata hai kilimanjaro.niroskos.com pe — tenant scoping tak ka full path batao.

💡 django-hosts maps subdomain → host pattern; middleware resolves tenant record, attaches to request (and contextvar for managers); TenantManager filters every ORM query; cache/search calls take tenant from the same context. Mention the contextvar-vs-threadlocal detail for async safety.

DEEP

Can a new developer on your team accidentally write a query that leaks another tenant's data?

💡 Honest answer: yes if they use objects.all() on a raw manager or raw SQL — mitigations: default manager IS the tenant manager, code-review checklist item, tests asserting cross-tenant requests get 404, and unscoped manager named loudly (e.g., all_tenants_objects).

CORE

Draw the Draft-to-Confirm state machine. Where exactly can it race?

💡 Practice drawing in <60s. Two race points to mark unprompted: (1) two users grabbing the last slot at Draft→Pending (fix: row lock/conditional update), (2) payment webhook confirming while expiry cron cancels the same booking (fix: both transition inside one transaction with select_for_update + state guard — loser sees changed state and aborts).

DEEP

Two users, last slot, same millisecond. Prevent the double booking — exact mechanism, not hand-waving.

💡 THE question for any booking system: SELECT ... FOR UPDATE on the availability/inventory row inside transaction.atomic, re-check availability after acquiring lock, decrement, create booking — all one transaction. Alternative: atomic conditional UPDATE with rows-affected check. Bonus: hold with TTL (expiry cron releases unpaid Drafts). Constraint as last line of defense.

CORE

M-Pesa sends the same payment callback three times. What does your system do on calls two and three?

💡 Idempotency: provider txn id unique-constrained on the payments table; handler does get_or_create / state-guarded update so only the first call transitions Pending→Confirmed and fires emails; duplicates return 200 silently (returning error makes the provider keep retrying).

TRAP ⚠

50,000 daily transactions is about 0.6 per second. What was actually hard about this system?

💡 Don't defend the number as scale — own the arithmetic instantly, clarify the unit (requests+events, peak-season bursts much higher), then pivot: the hard parts were correctness (double-booking, payment idempotency, multi-currency, Web3 confirmation latency) and tenant isolation, not raw QPS.

DEEP

Ethereum payment: booking ko paid kab mark karte ho — transaction submit hote hi ya mine hone ke baad? Reorg ho gaya to?

💡 Never on tx-hash submission: wait N block confirmations (e.g., 6-12) via poller/webhook checking the receipt; booking sits in Pending Payment with the tx hash recorded; reorg before N confirmations = treated as unpaid, re-verify. Volatility/conversion handled by pricing in fiat and converting at quote time.

CORE

Why Typesense and not Elasticsearch — you have Elasticsearch on your skills line too?

💡 Right-sizing: Typesense = single binary, instant typo-tolerant search, trivial ops for catalog-sized data; ES shines at log-scale aggregations/cluster scale — overkill here. This 'I chose smaller deliberately' answer is a senior signal; also be ready for one ES basic since it's on the skills line.

CORE

Multi-language i18n — kaise implement kiya? UI strings aur package descriptions, dono ke liye same mechanism hai kya?

💡 Two layers: Django gettext + LocaleMiddleware for static UI strings; DB-level translation for content (translated fields per language via modeltranslation-style columns / JSON / translation rows) for package descriptions. Language negotiated via URL prefix, subdomain or Accept-Language; per-language slugs + hreflang tie into the SEO claim; fallback to default language when a translation is missing.

CORE

Refund approval workflow — who approves, and what happens to inventory on refund?

💡 Refund request → state Refund Requested → back-office role approves (RBAC) → provider refund API call (async, can fail — retry/manual queue) → booking → Cancelled, inventory released back. Partial refund rules per cancellation policy/cutoff days.

▶Story 4: End-to-end invoicing system (Rs 50 Cr+ / 10,000 invoices/month / gapless numbering / proration)10 Q · 4 drillsP0 · MUST

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Walk me through the life of one invoice — from the moment it's triggered to the moment it's paid.

💡 Trigger (monthly cron / PO completion) → draft with lines + GST computation → posting assigns gapless number in a locked transaction → PDF render + email (async) → SAP push with idempotency key → payment reconciliation marks paid. Fluent in under 2 minutes.

CORE

Invoice numbers gapless kyun hone chahiye India me, aur tumne kaise implement kiya?

💡 GST compliance: consecutive serial number per financial-year series; gaps invite audit questions. Implementation: sequence/counter row per series, select_for_update inside the posting transaction, number assigned at post-time only. Know your actual series format (e.g., YEB/2025-26/00421).

DEEP

Why not just use a Postgres SEQUENCE or the row id for the invoice number?

💡 Sequences are non-transactional by design — a rolled-back transaction still consumes the value → gap. Gapless requires a transactional counter with a row lock, which serializes posting — acceptable trade-off at ~330/day, and you scope the lock per series so different series don't contend. This exact exchange is a favorite at India fintech/ERP interviews.

CORE

Your monthly generation cron dies after 1,800 of 3,000 customers. You re-run it. What happens — duplicates? missed customers?

💡 Neither: unique (customer, period) + get_or_create means done customers no-op; per-customer transaction means the 1,800 are committed; re-run completes the remaining 1,200. Say the word 'idempotent' and prove it with this mechanism.

DEEP

Rental starts on the 17th of a 31-day month at Rs 45,000/month. Show me the proration — and tell me where float would have burned you.

💡 Decimal('45000')/31×15 days, quantize to 2 places with declared rounding mode; float accumulates binary-representation error across 10k invoices → paisa mismatches with SAP/finance recon. Also state your policy: round per line item, then tax on rounded base (consistency matters for GST).

CORE

Finance says invoice YEB/0421 was posted with the wrong amount. Fix it.

💡 Never edit/delete a posted GST invoice: issue credit note referencing 0421 (full or partial), re-issue corrected invoice with the next number; both sync to SAP; audit trail intact. Bonus: mention the e-invoice/IRN angle — registered invoices need credit notes, not deletion.

CORE

What is a delivery challan and how does it relate to the PO and the invoice?

💡 Challan = goods-movement document (equipment dispatched to site); PO says ordered, challan says delivered, invoice says billed — 3-way match before posting. Have one mismatch story: e.g., partial delivery → invoice only challan'd quantity, balance billed next cycle.

DEEP

Month-end pe 3,000 invoices banti hain — PDF, SAP push, email sab ke saath. Kitna time lagta hai aur bottleneck kya hai?

💡 Have YOUR real duration. Architecture answer: Celery fan-out in chunks; bottleneck = PDF render + SAP API latency, so those run outside the numbering lock; SAP pushes rate-managed; DB work per invoice is milliseconds. If asked to make it 10x faster: parallel queues, pre-rendered templates, SAP batch endpoints.

TRAP ⚠

Two finance users click 'Post' on the same draft invoice simultaneously. What happens?

💡 State-guard + lock: posting re-reads the invoice with select_for_update, checks state=='draft' before proceeding; loser sees 'posted' and aborts → one number, one SAP push. If you only check state without the lock, both can pass the check — say why.

CORE

How does payment reconciliation actually mark an invoice paid?

💡 Payments pulled from SAP (or bank feed) → matched on invoice reference first, fallback amount+customer+date window → full match marks Paid, partial creates partial-payment record, unmatched lands in a suspense queue for finance with a daily report.

Why exactly 5 minutes for the token TTL — why not 30 minutes, why not cache until expiry?

💡 Needs a real reason: SAP token/session validity (name it) minus safety margin so you never send a token that dies mid-request; short TTL also bounds staleness if a token is revoked. Close with 'it's a config value we tuned' — but lead with the SAP expiry.

In-memory caching with 4 Gunicorn workers — kitne tokens honge? Koi problem?

💡 One per worker process (in-memory is per-process). Acceptable: tokens cheap, SAP allows concurrent sessions. WARMUP

List vs tuple — difference, and when would you deliberately pick a tuple?

💡 Mutability; tuple is hashable so it works as dict key / set member; slightly less memory + signals fixed structure (e.g. DB row, (lat, lng)).

CORE

Is Python pass-by-value or pass-by-reference? Prove it with a list and an int.

💡 Neither — pass-by-object-reference (call by sharing). Mutating a passed list (lst.append) is visible to the caller; REBINDING (lst = [] or x += 1 on int) is not, because the local name just points elsewhere. Asked in almost every India Python round — answer with the two-line code demo.

CORE

How does a Python dict work internally? Why is lookup O(1)?

💡 Hash table: hash(key) maps to a slot, collisions resolved by open addressing (probing), resize at ~2/3 load. Insertion order preserved since 3.7 (compact dict). Keys must be hashable — that's why list can't be a key but tuple can.

CORE

a = 256; b = 256; print(a is b) — and same with 257. What prints and why?

💡 True then (usually) False. CPython caches small ints -5..256; `is` checks identity, == checks value. Rule: `is` only for None/True/False.

TRAP ⚠

def add_item(item, items=[]): items.append(item); return items — call it twice with different items. What's the bug?

💡 Default list created once at def time, shared across all calls — second call returns both items. Fix: items=None, create [] inside. India interviews ask this almost every time.

CORE

Shallow vs deep copy — I have orders = [[1,2],[3,4]], I do copy.copy(orders) and modify a nested list. What happens?

💡 Both change — shallow copy duplicates outer list only, inner lists are shared references. deepcopy recursively copies. list[:], dict.copy(), copy.copy() are all shallow.

TRAP ⚠

funcs = [lambda: i for i in range(3)]; what does calling each print? Fix it.

💡 All print 2 — closures bind the VARIABLE, looked up late at call time (LEGB). Fix: lambda i=i: i (default captures value now) or functools.partial.

CORE

Explain *args and **kwargs — then write a function signature with positional, *args, a keyword-only arg, and **kwargs in valid order.

💡 def f(a, *args, timeout=30, **kwargs). args=tuple of extra positionals, kwargs=dict of extra keywords; * and ** also unpack at call site. He should write this without hesitation — it's the basis of every decorator.

DEEP

How does Python manage memory? When does garbage collection actually run?

💡 Refcounting frees most objects instantly at zero refs; the generational GC (gc module, 3 generations) exists only to break reference cycles. Mention: id() = address in CPython, memory may not return to OS, sys.getrefcount().

DEEP

You need to check membership of incoming IDs against 1 million existing records — list, set, or dict? And how do you load the 1M without killing RAM?

💡 set/dict O(1) vs list O(n). Stream with a generator (file iteration / .iterator() on querysets / csv chunks) instead of loading everything. Ties directly to his i3infosoft 1M-records bullet — expect this exact probe.

TRAP ⚠

Why is building a string with += in a loop slow, and what do you do instead?

💡 str is immutable — each += allocates a new string, O(n^2) total. Use ''.join(parts) or io.StringIO. Bonus: same logic explains why tuple has no append.

▶Python Concurrency — GIL, Threading vs Multiprocessing vs Asyncio (vs Celery)11 Q · 4 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Concurrency vs parallelism — difference in one line, and which does each Python tool give you?

💡 Concurrency = dealing with many things at once (interleaved); parallelism = doing many things at once (multiple cores). threading/asyncio = concurrency only (GIL); multiprocessing/Celery prefork = true parallelism. Standard India opener before the GIL question.

WARMUP

What is the GIL and why does Python have it?

💡 Global Interpreter Lock — per-process mutex so only one thread runs Python bytecode at a time; protects refcount-based memory management. Released during I/O and C-extension work. Not a Python-the-language thing — a CPython thing.

CORE

If the GIL allows only one thread at a time, why would threads still speed up your 10,000 SAP API calls?

💡 Because each thread releases the GIL while blocked on the socket — network waits overlap. 10 threads x 1s calls ≈ 1s wall time instead of 10s. CPU-bound code gets NO speedup from threads — that's the follow-up they want.

CORE

I/O-bound vs CPU-bound — which concurrency tool for each, with one example from your work?

💡 I/O (SAP calls, DB, S3) -> threads/asyncio; CPU (PDF/WeasyPrint rendering, data crunching) -> multiprocessing or a Celery worker. Saying the decision rule fast and confidently is 80% of this answer.

CORE

asyncio vs threading — what's actually different about the model?

💡 asyncio: ONE thread, cooperative — coroutines yield only at await, event loop schedules them, cheap (scales to 10k+ connections), but one blocking call stalls everything. Threads: preemptive OS scheduling, can be interrupted between any bytecodes -> race conditions, heavier per-thread cost.

CORE

Your resume says async processing via Celery — why Celery and not just asyncio or a background thread for invoice sync?

💡 Task must survive process restarts/deploys -> broker (RabbitMQ) persists it; need retries with backoff, scheduling (beat for his 12+ crons), and independent worker scaling. asyncio/thread = in-process, dies with the web worker, no durability. THE killer question for his resume — must be reflex-level.

delay() aur apply_async() me kya difference hai? Aap kab kaunsa use karte the?

Walk me through what happens end-to-end when your Django view calls invoice_task.delay() — every component till the result lands.

CORE

Worker EC2 instance crash ho gaya jab invoice-sync task aadha chal raha tha. Us task ka kya hota hai?

💡 Default (early ack): message already acked -> task silently lost. acks_late=True: unacked message redelivered to another worker -> runs AGAIN -> task must be idempotent. Bonus: task_reject_on_worker_lost for SIGKILL/OOM case.

CORE

How did you configure retries for SAP HANA failures? Exponential backoff actually kaise kaam karta hai?

CORE

Your resume says 'idempotent operations'. Show me concretely — in code terms — how your invoice-push task is idempotent.

💡 Before push: check if SAP doc number already stored for this invoice id; after success: persist external ref atomically; DB unique constraint on (invoice, period) as the hard guarantee. Rerun = no-op, not duplicate posting.

CORE

Why route tasks to separate queues? Aapne kaise kiya tha?

💡 task_routes mapping + dedicated worker -Q sap_sync. Reason: isolation — month-end 10k invoice burst must not delay fast user-facing tasks; slow queue workers scale independently. One queue for everything = head-of-line blocking.

DEEP

SAP ka HTTP call hang ho gaya aur task atka hua hai — Celery me iske against kya protection lagayi thi?

💡 Three layers: requests timeout param on the SAP call itself (first line), soft_time_limit raises SoftTimeLimitExceeded inside the task -> catch, cleanup, retry; hard time_limit SIGKILLs the worker child as last resort. Hard kill + acks_late = redelivery, so idempotency again. Naming all three layers is the senior answer.

DEEP

prefetch_multiplier kya hai, aur long-running tasks ke saath kya gadbad karta hai?

💡 Worker reserves prefetch_multiplier × concurrency messages upfront. One long task means its prefetched messages sit reserved while other workers idle. Fix: prefetch_multiplier=1 + acks_late for long/uneven tasks; high prefetch only for tiny fast tasks.

DEEP

Worker concurrency kaise decide ki? Prefork vs gevent/eventlet — SAP-push jaise IO-bound tasks ke liye kya sahi hai?

💡 Prefork (default) = processes, right for CPU-bound or C-extension work, concurrency ~ cores; gevent/eventlet = greenlets, hundreds of concurrent IO-bound HTTP calls (SAP push is exactly this) on one process. Caveats: gevent needs monkey-patching, DB connection pool limits become the real cap. Knowing -c and -P flags = hands-on signal.

DEEP

Raat 2 baje invoice task fail hua — aapko kaise pata chalega? Monitoring story batao.

💡 Flower for live worker/task state, task_failure signal -> Sentry/Slack alert, queue-depth alarm on RabbitMQ, logs correlated by task_id. 'Subah logs check kiye' is the answer that fails this question.

TRAP ⚠

Ek Celery task ke andar se dusra task .delay() karke .get() kar liya. Problem?

💡 Classic deadlock — worker blocks waiting for a result that needs a free worker. Celery raises RuntimeError by default. Correct tool: chain/chord/group (canvas), never sync-wait inside a task.

TRAP ⚠

Why Celery at all — Python threads ya asyncio se invoice push kyun nahi kar diya?

💡 Threads/asyncio die with the request process and deploys, no persistence/retry/visibility. Celery gives durable broker-backed queue, automatic retries, horizontal scaling across machines, scheduling. asyncio = IO concurrency inside a process, not durable background work.

DEEP

Redis result backend me kya store hota hai, aur kabhi clean na karo to kya hota hai?

💡 Per-task-id state + return value. Default result_expires=24h; without it Redis memory bloats at 10k+ tasks/month scale. Best: ignore_result=True for fire-and-forget tasks (most of his) — saying this signals production experience.

WARMUP

Producer se consumer tak message flow samjhao — exchange, binding, routing key, queue.

💡 Publish goes to an EXCHANGE (never directly to queue) with a routing key; bindings decide which queue(s) get it; direct=exact key match, topic=wildcard (*.invoice.#), fanout=broadcast all bound queues; consumer acks after processing.

CORE

RabbitMQ server restart hua aur queue me 500 invoice messages pade the. Kya bache, kya gaya? Kaise guarantee karte ho?

💡 Need durable=True queue AND delivery_mode=2 (persistent) messages — either one missing = loss. Celery defaults to both. Subtle third gap: a message published moments before crash without publisher confirms can still vanish.

CORE

Consumer ne message receive kiya aur process karte karte crash ho gaya — message ka kya hota hai?

💡 Unacked message is requeued when the channel/connection closes and redelivered (redelivered=true flag) to another consumer. That's at-least-once delivery — the reason invoice tasks must be idempotent. Manual ack mode is the prerequisite.

CORE

Dead-letter exchange kya hai? Apne invoice pipeline me kahan lagaoge?

💡 Queue declared with x-dead-letter-exchange; messages route there on reject/nack(requeue=false), TTL expiry, or max-length overflow. Use: after Celery max_retries, park the poison invoice in a DLQ for manual inspection instead of infinite redelivery loop blocking the queue.

DEEP

prefetch_count=1 vs prefetch_count=100 — difference kya, kab kya?

💡 QoS cap on unacked messages per consumer. =1: fair dispatch, no worker hoards messages — right for long uneven tasks like SAP sync. High: fewer network round trips, throughput for tiny fast tasks. Connect it to Celery prefetch_multiplier to show you've tuned it.

DEEP

Publish karte waqt network blip aa gaya — kaise pata broker tak message pahuncha ya nahi?

💡 Publisher confirms (confirm.select): broker acks each publish; without it publishing is fire-and-forget. In Celery terms: task_publish_retry handles connection errors on publish; confirms are not on by default — knowing this gap is a senior signal.

TRAP ⚠

Production me ek queue me 1 lakh messages jam ho gaye, consumers piche hain. Abhi kya karoge?

💡 First find root cause (downstream SAP slow? consumer crashed?) — check unacked vs ready in mgmt UI. Then: add competing consumers, raise prefetch for short tasks, lazy queues to protect memory. Wrong answer: purge the queue. They're testing incident composure.

TRAP ⚠

RabbitMQ exactly-once delivery deta hai na?

💡 No. At-least-once (manual acks, duplicates possible on redelivery) or at-most-once (auto-ack, loss possible). Exactly-once needs consumer-side dedup/idempotency — loop back to your invoice unique-key pattern.

CORE

Celery sab abstract kar deta hai — phir AMQP internals kyun aane chahiye aapko?

💡 Debugging: every Celery queue is an AMQP queue, task_routes are routing keys, 'lost tasks' are ack-semantics bugs. Real example: diagnosing unacked pileup in management UI when a worker hung. Without AMQP knowledge you're blind in production.

DEEP

RabbitMQ ke liye kya monitor karte the?

💡 Queue depth (ready), unacked count, consumer count, connection/channel churn via management UI or /api. Alert rule: queue depth growing + consumers flat = consumers dead or behind. Memory/disk alarms block publishers — worth mentioning.

Visibility timeout kya hai? Worker usse zyada time le le to kya hota hai?

💡 After receive, message hidden for the timeout; not deleted in time -> visible again -> another consumer processes it = duplicate. Fix: timeout > worst-case processing, or heartbeat ChangeMessageVisibility for long jobs.

Standard vs FIFO queue — invoice events ke liye kaunsa loge, aur FIFO ki cost kya hai?

💡 FIFO if per-customer ordering matters (MessageGroupId=customer_id) + dedup id; cost: 300 msg/s (3000 batched) throughput cap. Mature answer: standard + idempotent consumer is usually enough — ordering requirements are often imagined.

CORE

SQS me DLQ kaise set hota hai? RabbitMQ ke DLX se kya alag hai?

💡 Redrive policy on source queue: maxReceiveCount exceeded -> message moves to the DLQ (just another queue). DLX differs: exchange-routing based, triggers on explicit reject/nack, TTL expiry, queue overflow — not only receive count.

TRAP ⚠

FIFO queue le liya, ab duplicates impossible — sahi?

💡 Wrong twice: dedup window is only 5 minutes (same dedup id after 6 min = accepted again), and consumer crash after processing but before DeleteMessage still reprocesses. Punchline: idempotency lives in YOUR code, not the queue — same lesson as Celery acks_late.

CORE

Long polling kya hai, short polling se better kyun?

💡 WaitTimeSeconds up to 20 — receive call waits for a message instead of returning empty; fewer API calls = less cost, lower latency. Short polling samples a subset of SQS servers and can return empty even when messages exist.

DEEP

💡 Lose: worker remote control commands, full event stream (Flower partially blind), fanout/topic routing, ack-based redelivery (becomes visibility-timeout based). Gain: zero broker ops, IAM auth, effectively infinite scale. This question doubles as proof you actually evaluated it.

CORE

Naya AWS-hosted project — SQS ya RabbitMQ, kaise decide karoge?

💡 Default SQS for plain work queues: managed, DLQ built-in, scales, no broker to babysit. RabbitMQ when you need routing topology, push-based low-latency consumption, pub/sub without bolting on SNS, or non-AWS portability.

▶AWS S3 + Presigned URLs10 Q · 2 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

S3 object storage hai — iska matlab kya? EC2 ki EBS disk se kaise alag?

💡 Object storage: flat namespace me key→object, access HTTP API se (file-system mount nahi), unlimited scale, 11-nines durability, har object ka URL. EBS = block device, ek EC2 se attached, OS filesystem. Certificates jaise user files S3 pe isliye — app server stateless rehta hai, disk full nahi hoti. India screening rounds ka classic opener.

WARMUP

Tumne S3 presigned URLs use kiye certificates ke liye — internally ye kaam kaise karta hai? S3 ko kaise pata URL valid hai?

💡 URL me SigV4 signature embedded hai jo mere AWS credentials se compute hua + expiry + operation; S3 signature verify karta hai — client ko koi AWS auth nahi chahiye; expiry ke baad 403.

CORE

Code me kaise generate kiya? boto3 ka exact call kya hai?

💡 s3_client.generate_presigned_url('get_object', Params={'Bucket': b, 'Key': k}, ExpiresIn=900). Upload ke liye 'put_object' ya generate_presigned_post. Ye 3-line code bina dekhe likhna aana chahiye.

CORE

Presigned URL ki maximum expiry kya hai? Client ko 30 din valid download link dena ho to?

💡 IAM user creds se max 7 days; EC2 role (STS temp creds) se URL session ke saath hi mar jata hai (~hours). 30 din ke liye: CloudFront signed URLs, ya better — apna API endpoint jo har request pe fresh sign kare.

CORE

Upload ke liye presigned PUT vs presigned POST — difference? Aur server se upload karwane ke bajaye direct-to-S3 kyun?

💡 POST policy me conditions laga sakte ho (max file size range, content-type) — PUT me size enforce nahi hota (Content-Type sign ho sakta hai). Direct-to-S3 = file bytes Nginx/Gunicorn se nahi guzarte, worker block nahi hota, bandwidth bachti hai.

DEEP

Certificate ka presigned URL WhatsApp pe leak ho gaya — ab kya hota hai? Security model kya hai?

💡 Jo bhi URL pakde, expiry tak download kar sakta hai — by design. Mitigation: short TTL (10-15 min), auth-check ke BAAD per-request signing, DB me sirf S3 key store karo URL nahi; QR me verification endpoint dalo, raw S3 URL nahi.

CORE

Bucket public tha ya private? Block Public Access kya block karta hai?

💡 Private + Block Public Access ON (public ACLs/policies override ho jaati hain). Access sirf IAM + presigned se. Bonus: ACLs legacy hain, ab default disabled — bucket policy is the way.

DEEP

1,000+ certificates/month — S3 me organise kaise kiya? Purane certificates ka kya?

💡 Key naming scheme (org/type/YYYY/MM/uuid.pdf), lifecycle rule for old objects → IA/Glacier ya expiry, versioning awareness. Apna real naming pattern yaad rakho — generic answer pakda jata hai.

TRAP ⚠

Kya main aisi presigned URL generate kar sakta hoon jiske liye mere paas S3 permission hi nahi hai?

💡 Haan — generation purely local signing hai, koi API call/permission check nahi hota. Par USE karte waqt signing identity ke permissions check hote hain, to URL 403 dega. Ye trap 4-6yr level pe common hai.

CORE

EC2 pe chal rahe Django app ne S3 credentials kahan se uthaye?

💡 Best: IAM role attached to EC2 (instance profile) — boto3 instance metadata (IMDSv2) se temp creds uthata hai, auto-rotate. Credential chain order batao: env vars → ~/.aws/credentials → instance metadata. Agar .env me keys the to honestly bolo + role kyun better hai explain karo.

TTL pucha jayega — number ready rakho.

Interviewer: 99.9% kaise measure kiya — kaunsa tool? Aur sub-200ms p50 hai ya p95?
Prep: 99.9% = ~43 min downtime/month — ye math zubani aani chahiye. Apna sach wala source fix karo (UptimeRobot pings / CloudWatch / nginx access logs me $request_time percentile) aur uska screen describe kar pao. Agar informal estimate tha to reframe: 'X months me zero unplanned downtime, Y se monitor karte the' — kabhi aisa tool mat bolo jo describe nahi kar sakte.

▶AWS EC2 + IAM + Secrets Manager10 Q · 2 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Security group aur NACL me kya difference hai?

💡 SG: instance-level, stateful, sirf allow rules, sab rules evaluate hote hain. NACL: subnet-level, stateless (return traffic ke liye explicit rule), allow+deny, rule number order. India interviews me ye 90% baar aata hai.

CORE

Tumhare EC2 pe Django app S3 access kaise karta tha — access keys ya kuch aur?

💡 Best answer: IAM role/instance profile, boto3 IMDSv2 metadata se temp creds leta hai, auto-rotation, disk pe kuch nahi. Agar tumne .env me keys rakhi thi to admit karo + role superior kyun hai wo explain karo — honesty + knowledge dono milte hain.

CORE

IAM user kab banaoge aur role kab?

💡 User = insaan / external system jo long-lived creds chahta hai. Role = AWS services (EC2, Lambda) aur cross-account access — temp creds, no rotation headache. Production compute pe hamesha role.

CORE

Certificate bucket ke liye least-privilege IAM policy likho — kaunse actions, kaunsa resource?

💡 Effect: Allow; Action: s3:PutObject, s3:GetObject; Resource: arn:aws:s3:::cert-bucket/certs/* — bucket-level list chahiye to s3:ListBucket alag se bucket ARN pe. s3:* on * bola to negative marking.

CORE

Resume me SQS/SNS likha hai — dono me kya difference, aur tumne kahan use kiya?

💡 SQS = managed queue: consumer PULL karta hai, ek message ek consumer process karta hai, visibility timeout, DLQ, at-least-once → idempotent consumer chahiye. SNS = pub/sub PUSH: ek publish → multiple subscribers (SQS/Lambda/email). Fan-out pattern = SNS ke peeche multiple SQS. RabbitMQ (jo tumne use kiya) se compare karo: broker khud chalana vs fully managed. Apna ek TRUE use-case ya honest 'evaluate kiya, RabbitMQ chuna kyunki X' ready rakho — bracket me likha hai to pucha jayega.

CORE

Production me DB password aur SAP HANA creds kahan rakhte the? .env kyun nahi kaafi?

💡 .env disk pe plaintext, git me leak hota hai, koi audit/rotation nahi. Secrets Manager: KMS encryption, IAM se access control, CloudTrail audit, RDS password auto-rotation; app boot pe get_secret_value se fetch karke cache. SSM Parameter Store free option — dono ka naam lo.

DEEP

Tumhara EC2 internet pe exposed hai — SSH hardening ke liye kya kiya / kya karoge?

💡 SG me port 22 sirf office/apne IP se, key-based auth only + PasswordAuthentication no, PermitRootLogin no, fail2ban. Senior answer: SSM Session Manager use karo — port 22 ka SG rule hi delete.

DEEP

EC2 stop karke start kiya, ab site down hai — kya kya check karoge?

💡 Public IP change ho gaya (Elastic IP nahi tha) → DNS purana IP point kar raha; services boot pe start nahi hue (systemctl enable gunicorn nginx nahi kiya tha); instance-store data gone vs EBS persists.

TRAP ⚠

Kya security group me deny rule laga sakte ho?

💡 Nahi — SG allow-only hai; jo allow nahi wo implicitly denied. Explicit deny chahiye to NACL. Default SG: inbound sab deny, outbound sab allow.

CORE

App server se RDS tak ka network access securely kaise set kiya?

💡 RDS publicly-accessible OFF / private subnet; RDS ke SG me inbound 5432 sirf app ke SECURITY GROUP se (SG-to-SG reference) — IP hardcode nahi, kyunki IPs badalte hain.

📄 “Cloud & DevOps: AWS (EC2, S3, RDS, IAM, SQS/SNS, Secrets Manager), Docker, Nginx, Gunicorn, GitHub Actions (CI/CD)”
Interviewer: Interviewer bracket ke andar line-by-line jayega: 'IAM me exactly kya kiya? Secrets Manager sach me use kiya ya sirf padha hai?' — har naam pe ek concrete jawab chahiye.
Prep: Har service ke liye EK true sentence ready karo: EC2 ('Django+Laravel apps host kiye, SG manage kiye'), S3 ('certificates, presigned URLs'), RDS ('Postgres, backups + parameter group'), IAM ('EC2 role for S3, least-privilege policy'), SQS/SNS (jo bhi sach hai), Secrets Manager ('RDS/SAP creds, boot pe fetch'). Jis pe 2 line bhi nahi bol sakte — ya 2-line true story banao practice se, ya resume se hatao. Apni hi skills line pe blank = instant red flag.
📄 “Developed an NFC product lifecycle tracker (PHP Laravel on AWS)”
Interviewer: Laravel app AWS pe kaise deploy hui — Django wale setup se kya alag tha?
Prep: Ek minute ka contrast ready rakho: PHP = nginx + php-fpm (ya Apache), Python = nginx + gunicorn; dono EC2 pe kaise coexist/deploy hote the. Ye dikhata hai ki deployment ka mental model language se upar hai — strong impression banata hai.

▶AWS RDS (PostgreSQL)7 Q · 1 drillsP1

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

RDS kyun liya, EC2 pe khud Postgres kyun nahi chalaya?

💡 Managed: automated backups+PITR, patching, Multi-AZ failover, CloudWatch metrics built-in. Trade-off bhi bolo: no superuser, limited extensions, zyada cost — trade-off bolne se senior lagte ho.

CORE

Multi-AZ aur read replica me kya farak hai? Kab kya use karoge?

💡 Multi-AZ: synchronous standby dusre AZ me, automatic failover, READ NAHI kar sakte — pure availability. Replica: asynchronous, read traffic le sakta hai, promote ho sakta hai — read scaling. Lag ka zikr karo. Ye is section ka #1 question hai.

CORE

Production DB ki backup strategy kya thi? Risky migration se pehle kya karte the?

💡 Automated backups retention (7-35 days) + PITR via WAL; Odoo 15→17 migration se pehle manual snapshot — YE TUMHARI REAL STORY HAI, isi se answer karo. Manual snapshot delete ke baad bhi bachta hai.

DEEP

Django app me 'FATAL: too many connections' aa raha hai — kya karoge?

💡 Math karo: gunicorn workers × connections per worker vs instance class ka max_connections; CONN_MAX_AGE tune; pg_stat_activity se idle connections dekho/kill; long-term fix = pgbouncer ya RDS Proxy. Celery workers bhi connections khate hain — mention karo.

CORE

RDS pe postgresql.conf edit nahi kar sakte — slow query logging kaise on karoge?

💡 Parameter group me log_min_duration_statement set karo (dynamic — no reboot), custom parameter group attach; logs CloudWatch Logs me publish kar sakte ho. Static params (jaise shared_buffers) reboot mangte hain.

DEEP

Slow query production me kaise pakdi aur fix ki?

💡 Slow query log / Performance Insights → top SQL by load → EXPLAIN ANALYZE → seq scan dikha → index banaya. Yahin apni '60% query time reduction through indexing' story sunao — ek REAL query + column + before/after number ready rakho.

TRAP ⚠

RDS instance delete kar diya — backups ka kya hota hai?

💡 Automated backups instance ke saath delete ho jaate hain (final snapshot ka option milta hai — hamesha lo); manual snapshots survive. 'Sab backups safe hain' bola to trap me fas gaye.

🎯 Resume Drills — teri exact lines pe attack aayega

📄 “Reduced Django ORM query execution time by 60% through indexing optimization and legacy module migration.”
Interviewer: Ye 60% kahan measure hua — RDS pe? Kaise pata chala kaunsi query slow thi, aur kaunsa index lagaya?
Prep: Tooling-chain ke saath story banao: slow query log / pg_stat_statements / django-debug-toolbar se pakdi → EXPLAIN ANALYZE me seq scan → specific index (kaunsa column, B-tree ya composite, kyun) → before/after ms numbers. EK concrete query ka example zubani yaad — '60%' bina example ke hollow lagta hai.

▶Docker9 Q · 1 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Image aur container me kya farak hai? Aur container VM se kaise alag hai?

💡 Image = read-only layered template; container = uska running instance + ek writable layer. Container host ka kernel share karta hai (namespaces + cgroups isolation), VM me poora guest OS — isliye container MBs me, seconds me start.

CORE

Apne Django app ka Dockerfile bolo — line by line, abhi.

💡 python:3.11-slim base, PYTHONDONTWRITEBYTECODE/PYTHONUNBUFFERED, WORKDIR, requirements pehle copy + install, phir code copy, non-root user, CMD gunicorn. Hesitation = 'maine kabhi likha nahi' ka signal. 3 baar khali kagaz pe likh ke jao.

CORE

Har build pe pip install dobara kyun chal raha hai? Kaise fix karoge?

💡 COPY . agar requirements install se PEHLE hai to har code change layer cache invalidate karta hai. Fix: COPY requirements.txt → RUN pip install → COPY . . Plus .dockerignore se junk files ka invalidation roko.

CORE

Multi-stage build kya hai aur tumne kahan use kiya / kahan karoge?

💡 Stage 1 (builder): gcc/build-essential se wheels banao; Stage 2: sirf wheels/site-packages COPY --from=builder. Result: chhoti image, attack surface kam — psycopg2/lxml jaise C-extension wale Python projects ka standard pattern.

CORE

docker-compose me kya services thin? Django Postgres container se kaise connect hota hai?

💡 web, db, redis, celery worker (+ beat). Host = SERVICE NAME ('db:5432') kyunki compose network me DNS hai — localhost bola to galat. pg data named volume pe. depends_on sirf start order — DB ready ka wait nahi, isliye healthcheck/wait-for script.

DEEP

Container start hote hi exit ho jata hai — debug steps?

💡 docker logs <id> pehle; exit code dekho (1 = app crash, 137 = OOM/SIGKILL); docker run -it --entrypoint bash image se andar jao; common cause: CMD background/daemon mode me hai — PID 1 ko foreground process chahiye (gunicorn daemon off).

DEEP

Production me container exit code 137 ke saath mar raha hai — kya hai ye aur fix?

💡 128+9 = SIGKILL = OOM killer. docker stats se memory dekho; gunicorn workers × per-worker RAM vs container memory limit ka math; workers kam karo ya limit badhao; memory leak ho to worker max-requests recycling.

TRAP ⚠

Container ke andar files save ki, container delete kar diya — data ka kya hua?

💡 Gaya — writable layer container ke saath delete hota hai. Persistence = named volume ya bind mount. Isliye Postgres ka data directory hamesha volume pe hota hai.

CORE

ENTRYPOINT aur CMD me kya difference hai?

💡 ENTRYPOINT = fixed executable (override ke liye --entrypoint flag chahiye); CMD = default arguments, docker run me aasani se override. Common combo: ENTRYPOINT script (migrations, wait-for-db) jo end me exec "$@" karta hai, CMD me gunicorn.

📄 “Cloud & DevOps: AWS (EC2, S3, RDS, IAM, SQS/SNS, Secrets Manager), Docker, Nginx, Gunicorn, GitHub Actions (CI/CD)”
Interviewer: 'Docker likha hai — whiteboard pe apna actual Dockerfile aur compose stack draw karo.'
Prep: Interview se pehle apna REAL Dockerfile + docker-compose.yml memory se 3 baar likho. Agar production deploy Docker ke bina tha (bare EC2 + systemd), to precisely bolo kya dockerized hai (local dev / CI me Postgres+Redis) — half-sach se confident sach better hai, kyunki follow-up me pakde jaoge.

▶Nginx + Gunicorn10 Q · 2 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

Gunicorn kya karta hai jo runserver nahi karta? Aur uske aage Nginx kyun chahiye?

💡 runserver single-threaded dev tool hai. Gunicorn = pre-fork WSGI server, multiple workers, process management. Nginx aage isliye: slow client ki request/response buffer karta hai (warna worker atka rehta hai), static, TLS, compression. 'Slow client buffering' bola to alag dikhoge.

CORE

Kitne gunicorn workers chalate the? Formula kya hai aur kab tootta hai?

💡 (2×CPU)+1 starting point — 2-core pe 5. Par blind nahi: har worker RAM khata hai aur DB connection kholta hai; zyada workers = OOM + too many connections. Real tuning load test/monitoring se.

CORE

Sync vs gevent vs gthread workers — tumhare SAP HANA integration wale app ke liye kya sahi tha?

💡 SAP API call = worker I/O pe blocked baitha hai. gevent (monkey-patched greenlets) ya gthread se wahi worker aur requests handle karta hai. CPU-bound kaam ke liye sync hi theek. FastAPI side me uvicorn workers + async. Apne workload se justify karo — yahi 4-6yr ka difference hai.

CORE

Production me HTTPS kaise enable kiya? Certificate kahan se aaya aur renewal kaise hota hai?

💡 Let's Encrypt + certbot (--nginx plugin) — free cert, 90 din validity, certbot ka systemd timer/cron auto-renew karta hai. Nginx: listen 443 ssl + cert/key paths, 80→443 redirect. TLS nginx pe terminate hota hai, gunicorn tak plain HTTP + X-Forwarded-Proto header. India me chhoti/mid companies ye almost hamesha puchti hain.

CORE

Users ko 502 Bad Gateway aa raha hai — debug ka exact sequence?

💡 1) nginx error.log — 'connection refused' (gunicorn down/wrong socket) ya 'upstream prematurely closed' (worker timeout-killed mid-request); 2) systemctl status gunicorn + journalctl; 3) gunicorn --timeout vs request duration; 4) recent deploy? OOM? Sequence me bolo, random nahi.

CORE

502 aur 504 me kya farak hai? Kya batata hai ye difference?

💡 502 = upstream ne galat/koi response diya — app crash ya gunicorn ne worker maar diya. 504 = upstream zinda hai par proxy_read_timeout ke andar jawab nahi — app SLOW hai. Ye ek line tumhe debugging me seedha sahi direction me bhejti hai.

DEEP

Ek report endpoint 2 minute leta hai aur timeout ho raha hai — kya karoge?

💡 Galat answer: dono timeouts 180s kar do. Sahi: Celery task me offload, turant task_id do, polling/webhook se result — tumhare paas already Celery + 12+ cron automations ki story hai, usse connect karo.

CORE

Django ke liye nginx server block ke important directives bolo.

💡 upstream/proxy_pass (port ya unix socket), proxy_set_header Host $host, X-Forwarded-For, X-Forwarded-Proto $scheme, location /static/ { alias ...; }, client_max_body_size, proxy_read_timeout. Socket vs port ka trade-off bonus.

TRAP ⚠

HTTPS nginx pe terminate hota hai, par Django redirect loop me fas gaya / http:// links bana raha hai — kyun?

💡 Django ko pata hi nahi ki original request HTTPS thi — nginx se use HTTP mila. Fix: proxy_set_header X-Forwarded-Proto $scheme + settings me SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https'). Bahut common production bug — yaad rakho.

DEEP

50MB file upload 413 de raha hai — kahan kahan fix karna padega?

💡 nginx client_max_body_size (default sirf 1MB), Django DATA_UPLOAD_MAX_MEMORY_SIZE, timeouts bhi. Senior twist: itni badi files server se guzaarni hi kyun — presigned URL se direct S3 bhejo (tumhari apni resume story).

🎯 Resume Drills — teri exact lines pe attack aayega

📄 “Cloud & DevOps: AWS (EC2, S3, RDS, IAM, SQS/SNS, Secrets Manager), Docker, Nginx, Gunicorn, GitHub Actions (CI/CD)”
Interviewer: 'Browser se request tumhare Django view tak kaise pahunchti hai — production me har hop batao.'
Prep: 60-second chain rehearse: DNS → EC2 SG :443 → Nginx (TLS terminate, static check, proxy headers add) → gunicorn master → free worker → Django middleware → view → response wapas, nginx buffer karke slow client ko deta hai. Ye chain bina rukke bolna is cluster ka minimum bar hai.
📄 “sub-200ms response”
Interviewer: 'sub-200ms kaise mila — latency kahan se aati thi aur kya tune kiya?'
Prep: Asli contributors naam lo: query indexing (60% wala win), Redis caching, sahi worker type, nginx gzip + static offload. Pata hona chahiye ye p50 hai ya p95, aur kahan dekha — nginx access log me $request_time log karna ek perfect concrete detail hai.

▶GitHub Actions (CI/CD)8 Q · 1 drillsP1

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

GitHub Actions workflow file ka structure kya hota hai?

💡 .github/workflows me YAML; on: (push/PR + branch filter), jobs: har job ek fresh runner pe, steps me uses: (marketplace action jaise actions/checkout@v4) ya run: (shell). needs: se job dependency.

CORE

Tumhari CI/CD pipeline exactly kya karti thi — step by step, trigger se production tak?

💡 YE is section ka guaranteed question hai. Apni REAL pipeline ka 2-min flow: PR pe lint+test (postgres service), main pe merge → deploy job → secrets se SSH → git pull → deps → migrate → collectstatic → gunicorn reload → health check. Fluent chahiye, reconstructed nahi.

CORE

Pipeline ko EC2 ki SSH key ya AWS creds kaise diye? Logs me leak nahi hote?

💡 Repo Secrets me store, ${{ secrets.X }} se access, GitHub logs me auto-masked. Kabhi YAML/code me nahi. Bonus: GITHUB_TOKEN least-privilege permissions, aur AWS ke liye OIDC federation = no stored keys — ye bolo to senior signal.

CORE

CI me tests ko Postgres aur Redis kaise mile?

💡 Job me services: postgres:15 + redis with health checks; test env me DATABASE_URL=postgres://...@localhost:5432. Healthcheck zaroori warna tests DB ready hone se pehle bhaag jaate hain.

DEEP

Deploy ke beech migration fail ho gayi — production ka kya hua aur pipeline ka kya?

💡 set -e se script wahi ruk jaye — restart tak nahi pahuncha to app old code pe chalti rahegi (partial deploy se bacho). Asli answer: backwards-compatible migrations (naya column nullable, do-step rename), migrate-then-switch order, aur rollback plan pehle se.

DEEP

Tumhare setup me zero-downtime deploy GitHub Actions se ho sakta tha? Kaise?

💡 Gunicorn graceful reload (systemctl reload / SIGHUP — master naye workers laata hai, purane drain hote hain) — simplest. Aage: do upstream processes, nginx switch (blue-green). Minimum: restart ke baad health-check endpoint hit karke hi success mark karo.

TRAP ⚠

Debugging ke liye workflow me secret echo kar diya — log me dikhega kya?

💡 Registered secret ki EXACT value GitHub auto-mask karta hai (*** dikhta hai) — par base64/substring/JSON-dump karke print kiya to masking bypass = leak. Isliye secrets kabhi print nahi karte, sirf env/step input me pass karte hain; galti se leak hua to secret ROTATE karo, log delete karna kaafi nahi.

CORE

Pipeline 10 minute leti hai, team frustrated — kaise tez karoge?

💡 actions/cache se pip deps cache, jobs parallel (lint || test), PR pe targeted tests + main pe full, docker layer caching agar image ban rahi hai. Numbers ke saath bolo: 'cache se install 3min→20sec'.

▶JWT, OAuth2 & RBAC (Security: JWT, OAuth2, RBAC)11 Q · 3 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

JWT ke teen parts kya hote hain, aur signature exactly kya guarantee karta hai?

💡 header (alg, typ) + payload (claims: sub, exp, iat) + signature. Signature = tampering detection + authenticity, NOT confidentiality — payload koi bhi base64-decode kar sakta hai.

CORE

DRF me JWT kaise implement kiya — kaunsi library, kya configure kiya?

💡 djangorestframework-simplejwt (ya PyJWT custom): DEFAULT_AUTHENTICATION_CLASSES me JWTAuthentication, SIMPLE_JWT settings (ACCESS_TOKEN_LIFETIME 15m, REFRESH_TOKEN_LIFETIME, ROTATE_REFRESH_TOKENS=True, BLACKLIST_AFTER_ROTATION), TokenObtainPairView/TokenRefreshView. Custom claims = TokenObtainPairSerializer override. India me library-level follow-up almost guaranteed hai.

CORE

HS256 vs RS256 — tum kab kaunsa chunoge?

💡 HS256: ek shared secret, fast, single-app fine. RS256: auth service signs with private key, baaki services sirf public key se verify — microservices me secret distribute nahi karna padta; rotation via JWKS.

CORE

User ka access token leak ho gaya — damage kaise minimise karoge aur revoke kaise?

💡 Short expiry (15 min) caps the window; refresh rotation + reuse detection kills the session family; Redis denylist of jti until exp; token_version per user for logout-all. Admit: pure stateless JWT me instant revoke impossible.

CORE

Niroskos back-office API ke liye JWT kyu liya, Django session kyu nahi?

💡 Multi-tenant subdomains + SPA/API clients = stateless tokens cross-service kaam karte hain, no session affinity/shared session store. Tradeoff acknowledge karo: revocation harder, payload visible — that maturity earns points.

CORE

Refresh token flow whiteboard pe draw karo — rotation aur reuse detection ke saath.

💡 Login → access(15m) + refresh(7d, hashed in DB). 401 → POST /refresh → new PAIR issued, old refresh invalidated. Old refresh reused = theft signal → revoke whole token family.

DEEP

Multi-tenant platform me JWT se tenant isolation kaise enforce kiya?

💡 tenant_id claim token me at issue time; middleware matches claim vs request subdomain; NEVER client-sent tenant id pe trust; tenant-A ka token tenant-B subdomain pe reject.

TRAP ⚠

JWT encrypted hota hai na? Sensitive data payload me rakh sakte hain?

💡 Nahi — signed hai, encrypted nahi. Payload publicly readable; PII/secrets kabhi nahi. JWE exists for encryption but rarely used — naming it shows depth.

CORE

OAuth2 ke flows batao — kaunsa kab? Tumne kahan use kiya?

💡 Auth code + PKCE = user-facing third-party login; client credentials = server-to-server (map this to SAP/MasterIndia token auth — fetch token with credentials, cache, refresh). Implicit/password deprecated bolna bonus.

DEEP

YES platform ka 'OTP auth with RBAC' design walkthrough do.

💡 OTP: secrets.randbelow 6-digit, HASHED at rest with TTL + attempt counter (Redis), per-phone rate limit → verified → JWT with role claim. RBAC: role→permission tables, DRF permission classes per endpoint.

TRAP ⚠

alg:none attack aur HS256/RS256 confusion attack kya hai?

💡 Library me allowed algorithms PIN karo, header ka alg kabhi trust nahi. Confusion attack: RS256 public key ko HMAC secret bana kar forged HS256 token verify karwana — algorithms=['RS256'] explicitly pass karo (PyJWT).

▶Security — HMAC, CSRF, OWASP, Passwords (HMAC webhook validation; CSRF Protection)11 Q · 3 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

CORE

Exotel ke liye HMAC webhook validation exactly kaise implement kiya — steps batao.

💡 request.body (RAW bytes, parse se pehle) pe HMAC-SHA256 with shared secret → hexdigest → header signature se hmac.compare_digest → mismatch = 401, no processing. Order matters: verify FIRST, then parse/enqueue.

CORE

hmac.compare_digest hi kyu? Normal == comparison me kya problem hai?

💡 Timing attack: == pehle differing byte pe ruk jata hai, response time leak karta hai → attacker byte-by-byte signature brute-force kar sakta hai. compare_digest constant-time hai.

DEEP

Attacker ne ek VALID webhook capture karke 1 ghante baad replay kiya — signature to sahi hai. Kaise pakdoge?

💡 Timestamp signed payload me + reject if older than ~5 min; event-id ka dedupe store (DB unique / Redis SETNX); last line of defense = idempotent processing so duplicate harmless.

CORE

Tumhare DRF APIs me CSRF protection chahiye ya nahi? Kab chahiye?

💡 Cookie-based auth (session) = chahiye, browser cookies auto-attach karta hai. JWT in Authorization header = browser auto-attach nahi karta → CSRF N/A. Concrete: DRF SessionAuthentication CSRF enforce karti hai, JWTAuth nahi.

WARMUP

Django me passwords kaise store hote hain? SHA-256 se hash karke store kar sakte hain kya?

💡 Plain fast hash (SHA-256/MD5) NAHI — GPU se billions/sec brute-force hota hai. Django default = PBKDF2-SHA256 with per-user salt + high iterations (slow by design); argon2/bcrypt better bolna bonus. Format: algorithm$iterations$salt$hash. OTP se contrast: OTP = hash + TTL + attempt cap.

WARMUP

Django SQL injection se kaise bachata hai? Kahan phir bhi vulnerable ho sakte ho?

💡 ORM queries parameterized hain. Danger: raw()/extra()/cursor.execute me f-string ya % formatting — always params argument. Uska legacy-PHP-migration context me ek real example ready rakho.

CORE

Public webhook endpoint ka full security checklist do.

💡 HTTPS only → HMAC verify on raw body → timestamp/replay check → persist raw event → enqueue Celery → fast 200. Plus: event-id dedupe, optional IP allowlist, separate URL with random path, no session auth on it.

TRAP ⚠

HTTPS already hai to HMAC ki kya zaroorat? Encrypted hi to hai sab.

💡 HTTPS = transport encryption, sender identity prove NAHI karta — URL jaanne wala koi bhi POST kar sakta hai. HMAC proves sender holds the secret + payload not tampered. Different layers, different jobs.

TRAP ⚠

HMAC secret rotate karna hai zero downtime me — kaise?

💡 Dual-key window: verification me old + new dono try karo jab tak provider switch complete na ho, phir old drop. Same pattern JWT signing key rotation ka bhi hai — bolna bonus.

CORE

OTP/login endpoint pe brute force kaise roka?

💡 Redis counters: per-phone + per-IP, attempt cap with lockout/backoff, OTP expiry 5 min, alert on spike. DRF throttle classes naam lo (AnonRateThrottle / ScopedRateThrottle).

DEEP

Niroskos public site pe CMS/user content tha — stored XSS ka risk kahan tha aur kya kiya?

💡 Rich-text CMS content (package/itinerary descriptions) DB me HTML ke saath store ho to har render pe fire hota hai. Sanitize on input (bleach/allowlist tags), escape on output, CSP header. JSON API + React auto-escaping mention karo but dangerouslySetInnerHTML trap bolo.

▶API Design — REST, Idempotency, Rate Limiting, Webhooks (REST API design, Webhooks, idempotent operations)10 Q · 3 drillsP0 · MUST

✅ Must-Know (tick karte jao)

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

WARMUP

401 vs 403? 400 vs 422? Duplicate resource create pe kya return karoge?

💡 401 = not authenticated, 403 = authenticated but forbidden. 400 = malformed, 422 = syntactically valid but semantically wrong (DRF mostly 400 deta hai — consciously bolo). Duplicate = 409 Conflict.

CORE

Tumhare resume pe 'idempotent operations for 10,000+ invoices/month' likha hai — concretely kaise banaya idempotent?

💡 Natural key (invoice number / SAP reference) + DB unique constraint + pre-push existence check; success ke baad external doc id store hota hai so retry detects 'already pushed'. This is THE bullet — ek precise mechanism bolo, vague 'we checked first' nahi.

CORE

Exotel 200 req/min limit hai, tumhe 5,000 numbers pe bulk campaign chalani hai. Client-side design karo.

💡 Sab Celery queue me → global throttle: Redis token bucket (~3 req/sec) ya single dedicated worker with rate cap → 429/limit errors pe exponential backoff + requeue → status webhooks se outcomes update. Mention: spread over ~25 min, business-hours window.

DEEP

Token bucket vs sliding window — difference aur tumhare case me kaunsa kyu?

💡 Token bucket: burst up to bucket size allowed, refill = sustained rate — provider limit respect karne ke liye conservative refill rakho. Sliding window: strictly smooth, no burst. Fixed window ka boundary-burst problem bolna depth dikhata hai (do adjacent windows ke edge pe effectively 2x limit nikal jata hai).

CORE

1M invoices ki listing API — offset pagination kyu nahi, cursor kaise?

💡 OFFSET 100000 = DB scans & discards 100k rows + concurrent inserts pe rows skip/duplicate. Cursor: WHERE (created_at, id) < (last_seen) ORDER BY created_at DESC, id DESC LIMIT 50 — index use hota hai, stable. DRF CursorPagination naam lo.

CORE

Payment/Exotel webhook receiver ka design batao — kya synchronous karoge, kya async?

💡 Sync (inline): HMAC verify + raw event persist + dedupe check + 200 return — sab <1s. Async (Celery): actual business processing. Reason: provider timeout pe retry karega → duplicate events → isi liye event-id dedupe.

DEEP

SAP invoice push pe network timeout aaya — push hua ya nahi, pata nahi. Ab kya?

💡 Classic ambiguous failure: blind retry = duplicate risk. Answer: retry SAFELY — pehle SAP me reference id se query karo (read-before-retry) ya SAP-side dedupe on external reference; plus nightly reconciliation job dono sides compare karta hai. Ye literally uske 'payment reconciliation' bullet ka core hai.

CORE

Breaking change aa rahi hai API me — versioning strategy kya hogi?

💡 Pehle pucho: kya additive ho sakta hai (new optional field)? Breaking ho to /v1 → /v2 URL versioning (sabse common, cache/log friendly), dono parallel chalakar deprecation window + client migration tracking, phir sunset.

TRAP ⚠

POST retry-safe hai kya? Network failure pe client ne order POST dobara bhej diya to?

💡 POST not idempotent → duplicate order. Fix: Idempotency-Key header — server key ke against response cache karta hai, repeat key = same response, no second order. PUT full-replace idempotent hai, PATCH technically nahi guaranteed.

DEEP

Ek consistent error response design karo — validation errors, 500s, tracing ke saath.

💡 {"error": {"code": "INVOICE_DUPLICATE", "message": ..., "details": [field errors], "request_id": ...}} — machine-readable code + human message; request_id logs se correlate hota hai; 5xx me kabhi stack trace/internal detail leak nahi.

▶SAP HANA Connector — Flagship Integration (bi-directional SAP HANA REST API connector)10 Q · 4 drillsP0 · MUST

❓ Questions (Practice Mode me hint chhup jayega — click to reveal)

CORE

SAP connector ka end-to-end architecture walkthrough do — 10 minute hai tumhare paas.

💡 Business flows pehle (4 flows + volumes: 10k invoices/month), phir layers: auth module → client wrapper → per-entity sync services → sync-log table → reconciliation cron → alerting. Diagram practice karo: 5 boxes, Django/Odoo left, SAP right, queue+log beech me.

CORE

Token caching 5-min TTL — 5 min hi kyu? Aur cache expire hote hi 2 requests ek saath aaye to?

💡 SAP token validity se thoda kam TTL = har request pe auth round-trip bachta hai. Race: dono threads token fetch kar lete hain — harmless if SAP allows parallel tokens; ya lock lagao. Plus refresh-on-401 as safety net. Confident, specific answer chahiye.

DEEP

Bi-directional customer sync — same customer dono systems me edit hua. Kaun jeeta?

💡 Per-entity/per-field source of truth define tha (e.g., master data ERP me, credit data SAP me); last-modified timestamps compare; ambiguous = conflict log → manual resolution. Echo-loop prevention bolo: sync-origin flag taaki apna hi update wapas na aaye.

DEEP

10,000 invoice push me item 7,034 pe failure aaya — kya hota hai? Rollback?

💡 Koi giant batch transaction nahi — per-invoice push with own status row. Failed = flagged in sync-log, baaki continue; retry cron failed ones re-picks; threshold cross hua to alert. 'Partial failure is normal in integrations' — ye framing senior lagti hai.

CORE

Payment reconciliation EXACTLY kaise hota tha — matching logic kya thi?

💡 SAP se incoming payment entries → match against open invoices by reference number + amount (+ date tolerance); partial payments allocate hoke balance update; unmatched → suspense bucket → daily report. Resume bullet hai — yahan hesitation = red flag.

DEEP

99% success rate — measure kaise kiya? Aur 1% failures ka lifecycle?

💡 Sync-log table per transaction (status, error, timestamps) → daily success-rate report. ~100 failures/month: categories (SAP validation, timeouts, locked records), auto-retry handles most, baaki manual queue. EK real failure story sunao — credibility instantly badhti hai.

TRAP ⚠

4,858 lines? Itna kyu — over-engineered to nahi?

💡 Defend with scope, not defensiveness: 4 flows × (field mapping + validation + error handling + retry + logging + tests). Ya honestly: mappings/boilerplate bulk hai, core logic ~X lines. Calm ownership > justification.

DEEP

Journal entry creation — accounting samajh ke kiya tha ya blind push? Debit-credit balance kaun validate karta tha?

💡 Journal entry = balanced debit/credit lines with GL accounts/cost centers; push se PEHLE balance validation (sum debit == sum credit) warna SAP reject karta. Ye dikhata hai domain samjha, sirf API call nahi maari.

DEEP

SAP 4 ghante down hai. Tumhara system kya karega?

💡 Local operations continue (decoupled), pending syncs queue/flag hote rehte, retries with backoff — SAP ko hammer nahi karte (circuit-breaker ya disable flag), monitoring alert fire, recovery pe catch-up cron. Graceful degradation story.

TRAP ⚠

Tumhara retry SAP me duplicate billing document nahi banayega — guarantee kaise?

💡 EK concrete mechanism: SAP doc pe external reference field set karte the → retry par pehle us reference se query (read-before-retry) ya SAP same reference pe existing doc lauta deta. 'Pata nahi, retry kar dete the' = interview yahin khatam.

Prep: Entity→direction matrix likh ke yaad karo (customers: ↔, invoices: →SAP, payments: ←SAP, journal entries: →SAP) + conflict policy + echo-loop prevention. Ye FLAGSHIP hai — whiteboard pe 5-box diagram 3 baar practice karo, interviewer yahan 10 min rukega.

CORE

You said protobuf is 'faster and smaller' than JSON. What is actually different on the wire that makes it so?

💡 Standard follow-up to the pitch — don't just repeat 'binary'. Four concrete mechanisms: (1) no string keys — each field is a 1-2 byte tag (field number + wire type); (2) varint integers — small numbers take 1 byte vs multiple ASCII digits; (3) schema known at both ends, so the payload carries zero self-describing structure; (4) parsing via generated code/C extension vs reflective text parsing of JSON. Then volunteer the cost: not human-readable — curl se debug nahi hota, grpcurl + server reflection chahiye. Knowing the trade-off unprompted = real-usage signal.

CORE

A message of yours is live in production. You need to add one field and delete another. Exactly what do you do, and in what order do you deploy?

💡 Add: new field, NEW number, never reuse old numbers. Delete: remove field but add `reserved` for its number and name. Old clients ignore unknown fields, new clients see zero-default for missing — so additive changes are deploy-order-safe; for semantic changes deploy the reader side first (usually servers), then writers. Trap inside the question: 'can I renumber to keep it clean?' — NO, wire format field number se identify hota hai.

CORE

Give me a real use case for each of the four gRPC call types — ideally from your own project.

💡 Don't recite textbook chat-app examples. Map to his domain: unary = price/availability lookup between services; server-streaming = pushing booking/invoice processing progress or live status to an internal consumer; client-streaming = bulk record/chunk upload; bidi = rare, say honestly 'evaluated but didn't need it' — honesty scores points. Mention Python: streaming handler is just a generator.

CORE

What happens if you call a gRPC method with no deadline and the server hangs? How did you handle deadlines in your services?

💡 This is THE production-maturity question. No deadline = client thread blocked forever → ThreadPoolExecutor workers exhaust → your own service goes down (cascading failure). Fix: `timeout=` on EVERY call (sensible default in a shared client wrapper), server checks `context.is_active()` for long work, propagate remaining budget downstream via `context.time_remaining()`. Ek chhota incident-style story banao — 'humne default 3s deadline enforce kiya wrapper me'.

CORE

Your client intermittently gets UNAVAILABLE errors calling another service. How do you debug and fix it?

💡 Structured answer: (1) classify — UNAVAILABLE is transient/connectivity, not app logic; (2) usual suspects — server restarts/deploys, idle connection killed by LB/firewall (fix: keepalive pings), channel created per-request (fix: reuse one channel); (3) mitigation — retryPolicy in service config: exponential backoff, max attempts, ONLY on UNAVAILABLE, ONLY idempotent methods. Saying 'we made the RPC idempotent so retries were safe' = senior signal.

CORE

How did you do authentication and logging on your gRPC services?

💡 Two layers: channel security (TLS, ya mTLS if both services internal — cert verify both sides) + per-call auth (JWT in metadata, validated in a server interceptor before handler; client interceptor attaches the token so callers don't repeat code). Logging/metrics bhi interceptor me — 'gRPC ka Django-middleware equivalent' analogy works great with Django interviewers.

CORE

Your whole stack is Django served by Gunicorn. Where does the gRPC server actually run — can Gunicorn serve it? How does it talk to your models?

💡 The 'did you really run it' filter question for a Django resume. No — Gunicorn/WSGI is HTTP/1.1 request-response and can't host gRPC's HTTP/2 streams. The gRPC server is a SEPARATE process: standalone entrypoint or `manage.py` management command that calls `django.setup()` first, so servicer handlers reuse the ORM/models/settings directly. Deployed as its own container/port next to the web container, with its own health check (grpc_health.v1 or a trivial Ping RPC). Alternative for a clean split: separate microservice with its own DB access. Bonus: DB connections in gRPC threads need the same care as Celery workers — close stale connections per call.

DEEP

You have gRPC, REST and RabbitMQ all on your resume. Service A needs data from service B — how do you decide which one to use?

💡 This should be his BEST answer — rehearse till smooth. Framework: (1) Does caller need the answer NOW to proceed? Sync → REST/gRPC; no → queue. (2) Sync + internal + both ends ours + perf/contract matters → gRPC; public/browser/third-party/webhooks → REST. (3) Async, fire-and-forget, spikes absorb karna hai, broker-level retry/DLQ chahiye → RabbitMQ/Celery. Close with one concrete decision you actually made and WHY — e.g., 'invoice sync stayed on RabbitMQ because consumer downtime shouldn't fail the producer; price lookup went gRPC because the caller blocks on it'.

DEEP

Python gRPC server under heavy load — how does it behave with ThreadPoolExecutor, what about the GIL, and how do you scale it?

💡 max_workers = hard concurrency cap; beyond that requests queue. GIL: fine for I/O-bound handlers (threads release GIL on I/O), bad for CPU-bound — scale with multiple processes (SO_REUSEPORT) or just multiple containers behind an L7 LB. Mention grpc.aio (asyncio API) as the modern alternative for high-concurrency I/O. And the LB gotcha: long-lived HTTP/2 connection pins to one backend on L4 — need L7/client-side LB. Yeh combo answer 6-yr level lagta hai.

TRAP ⚠

💡 Two traps in one. Browser: NO native gRPC (browsers can't control HTTP/2 frames) — you'd need gRPC-Web + Envoy proxy or a REST gateway; that's why public APIs stay REST. 'Use everywhere': binary = harder to debug (curl se nahi, grpcurl/reflection chahiye), team learning curve, ecosystem tooling (caching/CDN/API gateways) is REST-first, and for low-traffic internal calls the perf gain doesn't pay for the complexity. Admitting gRPC's costs = maturity, fanboy mat bano.
